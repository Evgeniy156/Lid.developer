## ⚙️ Блок 2: Архитектура проекта

---

**Q5. Почему старый импорт переписывали?**

> Там была классическая legacy-ситуация: 100+ скриптов, у каждого своя реализация скачивания, парсинга, маппинга и записи в базу. Полная копипаста. Добавить нового поставщика — это написать ещё один скрипт. Поменять логику нормализации — залезть в каждый из ста файлов. Плюс большие файлы периодически падали с Out of Memory.
>
> Решение — config-driven подход: поставщик описывается JSON-конфигом, а один worker-runtime обрабатывает всех. Новый поставщик — это конфиг, не код.

---

**Q6. Почему разделили на несколько сервисов?**

> У каждой части свой характер нагрузки. HTTP-эндпоинт должен отвечать за миллисекунды — он просто ставит задачу в очередь. Тяжёлый worker с потоковым чтением файла может работать минуты. Если это одно приложение — они мешают друг другу.
>
> Получилось так: `supplier-settings-service` хранит конфиги, `import-control-service` создаёт import run и кладёт job, `import-planner` выбирает нужную очередь, channel worker-ы делают саму работу.

---

**Q7. Как выглядел полный поток запуска импорта?**

> Начинается с `POST /internal/import-runs` — валидация DTO, запись статуса в `import_runs`, job в BullMQ. Дальше planner-worker читает config поставщика и кладёт job в нужную channel-очередь: API, Excel, browser или OCR. Channel worker забирает, читает данные потоком, маппит, валидирует — и batch upsert в `supplier_offer_snapshots`. В конце Kafka-событие `supplier_offers.changed` для downstream-сервисов.
>
> Ошибки строк — в `import_run_errors`. Если включён debugMode — raw и normalized rows пишутся во временную таблицу для разбора.

---

**Q8. Как не ломали production при миграции с legacy?**

> Никакого «выключили старое, включили новое». Переводили постепенно — сначала MVP на паре поставщиков, смотрели как работает, расширяли. Старые скрипты ещё долго работали параллельно для стабильных поставщиков. Для спорных случаев включали debug-режим и сравнивали: сколько строк приняли, сколько rejected, есть ли расхождения в changed offers. Только при уверенности переключали.

## 💻 Блок 3: Node.js и JavaScript

---

**Q9. Как работает event loop в Node.js?**

> Один поток, но I/O неблокирующий. Пока база думает или файл качается — event loop не стоит, он обслуживает другие запросы. Главная ловушка — синхронные тяжёлые вычисления: они блокируют весь поток и всё встаёт.
>
> В импорте это конкретная проблема: если парсить Excel синхронно на полмиллиона строк — event loop замёрз. Решение — потоковое чтение чанками с паузами между batch-операциями.

---

**Q10. Зачем использовали streams в импорте?**

> Прайс поставщика — это легко 200-500 МБ. `readFile` на таком файле — и Node.js пытается всё это запихнуть в heap. Процесс падает с OOM, сервер плохо себя чувствует. Stream читает файл кусками: 500 строк → нормализовали → сбросили в Postgres → память освободилась → читаем следующие 500. Можно обрабатывать файл любого размера с предсказуемым потреблением памяти.

---

**Q11. Как контролировали потребление памяти?**

> Смотрел на размер входных данных, batch size и количество параллельных worker-ов. После flush батча делал `batch.length = 0` чтобы освободить массив. Ограничивал concurrency worker-ов через BullMQ, чтобы не запускать 50 тяжёлых задач одновременно.

---

## 🔷 Блок 4: TypeScript и ООП

---

**Q12. В чём разница между `class` и `interface` в TypeScript?**

> `class` живёт в runtime — из него можно создать объект, на него вешаются декораторы NestJS и class-validator. `interface` исчезает после компиляции — это только подсказка TypeScript-компилятору о форме данных.
>
> На практике: DTO для HTTP-запроса — это класс, потому что `ValidationPipe` работает с ним в runtime. А вот форму конфига поставщика или payload Kafka-события описываю через `interface` или `type` — в runtime они не нужны.

---

**Q13. Зачем union types и type guards?**

> Union type описывает несколько допустимых вариантов. Канал импорта может быть `'api' | 'spreadsheet' | 'browser' | 'ocr'` — у каждого свой config с разными полями. Type guard проверяет данные в runtime и сужает тип для TypeScript.
>
> ```ts
> function isApiConfig(c: SourceConfig): c is ApiConfig {
>   return 'baseUrl' in c && typeof c.baseUrl === 'string';
> }
> ```
> Конфиги приходят из JSON, поэтому на compile-time им нельзя доверять полностью.

---

**Q14. Почему избегали `any`? Чем `unknown` лучше?**

> `any` — это выключатель TypeScript. Поставил `any` и компилятор перестаёт проверять — ошибки проявятся только в проде. `unknown` честнее: «данные есть, но я не знаю что это». Чтобы что-то с ними сделать — сначала проверь тип. Для данных из внешнего JSON это правильный паттерн: `unknown` → type guard → конкретный тип → работаем спокойно.

---

**Q15. Где использовали generics?**

> Для типизированных HTTP-клиентов, event envelope и reusable helpers. Например, `ApiResponse<TData>` — один тип для всех ответов API, при этом `data` всегда типизирована.

## 🏗️ Блок 5: NestJS

---

**Q16. Как устроен Nest module?**

> Module — коробка, которая регистрирует controller-ы и provider-ы. Nest читает метаданные из `@Module`, строит граф зависимостей и внедряет их через конструктор. В import-control module регистрируем controller, service, repository и queue producer.

---

**Q17. Что такое Provider и DI?**

> Provider — класс, который Nest создаёт и внедряет. DI — когда класс не делает `new Dependency()`, а получает зависимость снаружи через конструктор. `ImportRunService` не знает, как создать Postgres-клиент — он просто получает repository и producer. Это снижает связность и упрощает тесты (легко подменить моком).

---

**Q18. Почему controller должен быть тонким?**

> Controller — транспортный слой. Принял HTTP, достал body/params, вызвал service, вернул ответ. Тяжёлая бизнес-логика, SQL, парсинг файлов — в service/application layer. Тонкий controller проще тестировать и use case можно вызвать не только из HTTP, но и из script/worker.

---

**Q19. Как валидировать вложенный массив объектов в DTO?**

> Нужны `@ValidateNested({ each: true })` и `@Type(() => ChildDto)` из `class-transformer`. Без `@Type` валидатор не поймёт, в какой класс превратить вложенный объект. `{ each: true }` говорит проверять каждый элемент массива.

---

**Q20. Для чего нужны Pipe, Guard, Interceptor, Filter?**

> - **Pipe** — валидация и преобразование входа (`ValidationPipe`)
> - **Guard** — проверка доступа и прав (JWT, роли)
> - **Interceptor** — обёртка вокруг запроса/ответа (логирование, метрики, маппинг ответа)
> - **Exception Filter** — единый формат ошибок для всех endpoint-ов

## 🗃️ Блок 6: PostgreSQL

---

**Q21. Приведи пример сложной сущности в базе.**

> `supplier_sources` — источник данных поставщика. Хранит channel, schedule, `source_config` (JSONB — разный для API/Excel/browser/OCR), `mapping_config`, `normalization_config`, `limit_config`.
>
> `supplier_offer_snapshots` — текущее предложение: артикул, бренд, цена, остаток, срок доставки, `content_hash`. Уникальность по (supplier, source, normalized_article, normalized_brand, sku).

---

**Q22. Какие индексы добавлял и почему?**

> Строил под реальные запросы, не вслепую. Для истории импортов — `(supplier_id, created_at DESC)`. Для поиска offers — `(normalized_article, normalized_brand)`. Для debug rows — `(import_run_id, row_number)`. После добавления проверял план через `EXPLAIN ANALYZE` — смотрел, нет ли Seq Scan там, где ожидался Index Scan.

---

**Q23. Как делал bulk upsert и зачем content_hash?**

> Собирал batch, строил один `INSERT ... VALUES (...)` с параметрами, на конфликте `ON CONFLICT DO UPDATE SET ... WHERE content_hash <> EXCLUDED.content_hash`. Если строка не изменилась — база не делает update, не создаёт WAL-запись, downstream не получает лишнего события.

---

**Q24. Где использовал JSONB?**

> В `supplier_sources` для конфигов: API, Excel, browser и OCR имеют разные настройки — нельзя сделать единую схему колонок. Часто используемые бизнес-поля (supplier_id, channel, schedule) держал обычными колонками. JSONB — только для вариативной части. Для частых JSONB-запросов можно добавить GIN-индекс.

---

**Q25. Как бы делал миграцию большой таблицы без простоя?**

> Поэтапно: добавить nullable колонку → писать в старую и новую → backfill мелкими батчами с паузами → проверить консистентность → переключить чтение → удалить старое. Индекс создавать `CONCURRENTLY`. Главный риск — долгий lock таблицы, который блокирует запись.

---

## 🚀 Блок 7: Очереди и асинхронность

---

**Q26. Зачем очередь (BullMQ), почему не cron напрямую?**

> Cron умеет запустить задачу в нужное время — и всё. Никакого контроля нагрузки. Если 100 поставщиков обновляются ночью — 100 тяжёлых процессов стартуют одновременно, сервер ложится. BullMQ решает это иначе: задачи в очереди, worker-ы разбирают их по мере освобождения — не больше N параллельно. Плюс retry с backoff, delayed jobs, видимость статусов и DLQ для задач, которые упали окончательно.

---

**Q27. Как работал retry/backoff?**

> Для transient-ошибок (таймаут API, сеть дёрнулась) job повторялась с exponential backoff: `attempts: 3, backoff: { type: 'exponential', delay: 1000 }`. Важно: ошибки данных не ретраить бесконечно — разделять transient errors и validation errors. Retry требует идемпотентной записи.

---

**Q28. Как обеспечивал идемпотентность?**

> Повторная обработка не должна создавать дубли. Для offers — unique key и upsert. Если worker упал после записи части batch-а, retry повторит upsert, но уникальный ключ не создаст дубликаты. Для Kafka-событий — correlationId/importRunId, дедупликация на стороне consumer-а.

---

**Q29. Что делал, если worker упал на середине импорта?**

> Import run переходил в failed, ошибка логировалась. BullMQ делал retry по attempts/backoff. Запись шла batch/upsert-ом и была идемпотентной — повторный запуск не ломал уже записанные строки. Ошибки строк писались в `import_run_errors` с importRunId для разбора.

---

## 📡 Блок 8: Redis и Kafka

---

**Q30. Чем BullMQ/Redis отличается от Kafka в вашей архитектуре?**

> Простое различие: BullMQ — «надо сделать работу», Kafka — «факт уже произошёл». Запустить импорт прайса — это job для BullMQ. После того как импорт завершился, публикуем `supplier_offers.changed` в Kafka — калькулятор цен и аналитический сервис подписаны на это событие и делают своё дело независимо. Импорт не знает о существовании калькулятора — слабая связность.

---

**Q31. Для чего использовал Redis?**

> В этом контуре Redis использовался как инфраструктура BullMQ и для временных вещей: **locks** с TTL (не дать запустить два импорта одного поставщика параллельно), **временные статусы**, **rate limit**. Источником истины оставался Postgres — нельзя хранить критичные бизнес-данные только в Redis.

---

**Q32. Как следил за лагом очередей?**

> Метрики в Grafana: waiting/active/failed jobs, возраст старейшей задачи, p95 processing time, retry count. Alert, если очередь растёт быстрее, чем worker-ы разгребают. По channel — масштабировать worker-ы там, где нагрузка выше.

---

## 🔌 Блок 9: Интеграции и парсинг

---

**Q33. Как парсил личные кабинеты поставщиков (browser automation)?**

> Если нет API и данные доступны только через B2B-портал — headless browser (Playwright). Программно логинимся, ждём CSS selector, забираем таблицу или скачиваем файл. В разработке — headed mode, в production — headless. Proxy rotation для источников с ограничением по IP. В тестах держали HTML snapshots, чтобы не дёргать реальный сайт в CI.

---

**Q34. Как работал с OCR/PDF?**

> Для PDF/сканов из email: вытаскивали текст OCR-ом → приводили к табличному виду → прогоняли через тот же mapping/validation pipeline. OCR не пишет напрямую в offers. Ключевой параметр — confidence threshold: строки ниже порога идут в rejected/debug на ручной разбор.

---

**Q35. Как устроен mapping config поставщика?**

> Небольшой DSL: внутреннее поле можно взять из колонки Excel, JSON path, regex, literal, concat или template. Так новый поставщик часто добавляется конфигом без нового кода. Конфиг валидируется на входе — иначе ошибка проявится только в worker-е при реальном запуске.

---

**Q36. Как подключить нового поставщика?**

> 1. Выясняем канал: API, файл, browser, OCR.
> 2. Создаём source config: URL/endpoint, auth, schedule, mapping, normalization, limits.
> 3. Запускаем debug import на fixture/малой выборке.
> 4. Проверяем rejected rows и changed offers.
>
> Если формат типовой — код не трогаем. Если новый формат — добавляем adapter/reader.

## ✅ Блок 10: Тесты и качество

---

**Q37. Какие автотесты писал?**

> Unit — чистая бизнес-логика без инфраструктуры: mapping rules, normalization, validation строки, расчёт content_hash, pricing rules. На вход raw row и config, на выход normalized offer или row error.
>
> Integration — repository с реальной test DB, upsert, смена статусов import run.
>
> E2E — полный сценарий: HTTP-запуск → очередь → worker → записи в БД → статус completed → событие.

---

**Q38. Как тестировал парсеры поставщиков?**

> Через fixtures: нормальный CSV, CSV с пустым артикулом, API JSON с pagination, HTML snapshot личного кабинета, OCR text с низким confidence. Для browser parsing — HTML snapshots, чтобы тесты не зависели от внешнего сайта.

---

**Q39. Что делал с flaky-тестами?**

> Убирал зависимость от реального времени (fake timers), заменял внешние API mock/fixture, ждал конкретный статус вместо `sleep`. Изолировал данные теста, чистил очереди/БД между тестами.

---

**Q40. Что проверял в MR (code review)?**

> Не просто стиль, а надёжность: что будет при retry? При падении worker-а? С плохими данными? С большим файлом? Нет ли `N+1` запросов? Нет ли `any` в TypeScript? Redis не стал источником истины? Логи не содержат секреты? Есть тесты на сложную логику?

## 📊 Блок 11: Мониторинг и инциденты

---

**Q41. Что логировал в системе?**

> В каждом логе: `importRunId`, `supplierId`, `sourceId`, `channel`, `correlationId`, `status`, `error_code`, `duration`. Все логи связаны через correlationId — можно найти весь путь одного import run от HTTP-запроса до Kafka-события.

---

**Q42. Какие метрики смотрел?**

> read/accepted/rejected rows, changed offers, queue waiting/active/failed, retry count, p95 duration batch upsert, ошибки внешних API, лаг consumer-ов Kafka. Alert — не на каждую ошибочную строку, а на системную деградацию (spike rejected rows, очередь растёт).

---

**Q43. Как разбирал инцидент?**

> Сначала смотрю на симптом — что именно выросло или упало: очередь, rejected rows, worker, скорость базы. По метрикам сужаю зону: это проблема источника данных, mapping-логики, базы или внешнего API поставщика? Потом беру `correlationId` или `importRunId` и иду по цепочке логов — от HTTP-запроса до последнего события. Обычно за 5-10 минут понятно где именно сломалось.

## 🛠️ Блок 12: Git, CI, Docker

---

**Q44. Какой был Git flow?**

> Feature branch от актуального develop, маленький MR, code review, зелёный CI, merge. В описании MR: что изменилось, как проверить, какие риски, есть ли миграции, backward compatibility. Большие фичи дробил на несколько безопасных MR.

---

**Q45. Что было в CI pipeline?**

> `install → lint → typecheck → unit tests → integration tests → build → docker image`. Для MR обязательно зелёный pipeline перед merge. Для миграций — отдельная проверка на test DB.

---

**Q46. Как запускал проект локально?**

> Через Docker Compose: поднимал Postgres, Redis, Redpanda/Kafka и нужные сервисы одной командой. ENV задавал подключения к инфраструктуре. Healthcheck помогал дождаться готовности базы и Redis перед стартом сервисов.

---

**Q47. Как работал с env/secrets?**

> Секреты никогда не хранил в git. В config лежит `secretRef`, реальное значение берётся из env/vault/CI variables. Локально — `.env` файл. В логах нельзя печатать токены, пароли, API keys, персональные данные.

## 📦 Блок 13: Пакеты и общий код

---

**Q48. Делал ли общий внутренний пакет?**

> Да. Выносили туда общие DTO/response types, event schemas (чтобы Producer и Consumer Kafka не разъезжались), queue payload types, кастомные ошибки, env helpers, test fixtures. Важно: бизнес-логику одного сервиса не тащить в общий пакет — иначе получится второй монолит.

---

**Q49. Как публиковали внутренние пакеты?**

> Два подхода: monorepo workspace (пакет доступен как workspace dependency без публикации) или private npm registry с версионированием через semver. Breaking changes — только major версией. Перед публикацией: lint, typecheck, tests, build.

## 🧠 Блок 14: Сложные технические вопросы

---

**Q50. Как бы реализовал партиционирование таблицы истории?**

> Партиционирование по дате имеет смысл для: огромной истории событий, отчётов по датам, очистки старых данных батчами. Для offer snapshot сначала смотрю на индексы и upsert. Для истории import runs/events партиционирование по дате — полезно при большом объёме.

---

**Q51. Как обеспечить ordering событий в Kafka?**

> Если порядок важен — нужен ключ партиционирования. Например, события одного `importRunId` или `supplierId` должны попадать в один partition и обрабатываться по порядку. Но не все события требуют глобального порядка — иногда достаточно порядка внутри одного поставщика.

---

**Q52. Что такое backpressure и как с ним бороться?**

> Если очередь растёт быстрее, чем worker-ы обрабатывают — нужно: ограничить входящий поток (rate limit на producer), увеличить количество worker-ов, уменьшить batch cost или разнести тяжёлые задачи по отдельным каналам с разными лимитами.

---

**Q53. Как запускал одноразовый script с DI-зависимостями в NestJS?**

> Создавал application context, доставал нужный service через `app.get(ServiceName)`, выполнял метод, закрывал приложение. Использовал для backfill, ручного запуска импорта, пересборки кэша, диагностики проблемных данных.

---

**Q54. Как делал rate limit для внешних API?**

> В config поставщика задавался `rateLimit: 10` (запросов в секунду). Worker реализовывал token bucket или использовал throttle-middleware. Для browser-парсинга — случайные задержки между запросами + proxy rotation, чтобы не получить бан по IP.

**Q55. Расскажи о своей слабой стороне.**

> Kubernetes — знаю на уровне разработчика: посмотреть логи, проверить env, понять почему pod не стартует. Но настройка кластера, Helm-чарты, сетевые политики — это не моя область, там нужен DevOps. Фронтенд — могу разобраться в чужом коде и сделать несложную задачу, но это явно не моя сильная сторона.
