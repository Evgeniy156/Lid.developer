## 2. Техника

### JS/Node
**Event loop, async, streams, память:**
- **Event Loop:** Один поток, I/O неблокирующий. Главная ловушка — синхронные тяжёлые вычисления: они замораживают весь поток. В импорте это реальная проблема — синхронный парсинг большого файла кладёт event loop.
- **Async/Await:** Обёртка над Promise. Worker берёт задачу, читает строки потоком, пишет батч — всё асинхронно, но читается как обычный последовательный код.
- **Streams:** Прайс — это легко 200-500 МБ. `readFile` целиком → OOM. Stream читает чанками: 500 строк → нормализовали → в базу → память освободили → следующие 500.
- **Память:** Слежу за batch size, concurrency worker-ов и размером входных данных. После flush делаю `batch.length = 0` — явно освобождаю массив.

### TS/OOP
**Class, interface, generic, type guard:**
- **Class vs Interface:** `class` существует в runtime (на него вешаем декораторы валидации DTO). `interface` или `type` существуют только в TS как контракты (удобно для payload'ов очереди).
- **Union & Type Guard:** Если канал может быть `'api' | 'spreadsheet' | 'browser'`, мы используем type guard (`isApiConfig`), чтобы безопасно сузить тип в runtime и защитить worker от неверного конфига.
- **Generic:** Использовал для общих ответов (например, `ApiResponse<TData>`) и типизированных HTTP-клиентов, чтобы не скатываться в `any`.
- **OOP / DI:** В NestJS чаще использую композицию. Service получает зависимости через конструктор (Repository, Queue Producer). Это позволяет легко мокать их в тестах.

### Nest/API
**Module, DI, controller, DTO:**
- **Module:** Коробка, которая говорит Nest, какие контроллеры и провайдеры (сервисы) существуют и как их связать.
- **DI (Dependency Injection):** Класс не создает зависимости сам (`new Client()`), а получает их снаружи.
- **Controller vs Service:** Контроллер — это транспорт (принял HTTP, распарсил DTO, отдал ответ). Вся логика и use-case (поставить в очередь, проверить БД) лежит в Service.

### Validation
**Nested DTO, pipes, errors:**
- Входящие запросы валидируем через `class-validator` (DTO).
- Для вложенных массивов объектов обязательно нужны `@ValidateNested({ each: true })` и `@Type(() => ChildDto)`, иначе Nest не поймет, в какой класс превратить вложенный JSON.
- Ошибки отлавливаем через глобальный `Exception Filter`, приводя их к единому стандарту для фронта/клиентов.

### Postgres
**Сущности, индексы, slow query:**
- **Сущность:** `SupplierSourceProfile` (конфиг источника) и `OfferSnapshot` (артикул, бренд, цена, остаток, хэш).
- **Индексы:** Строил не вслепую, а под конкретные `WHERE` и `JOIN`. Например, составной индекс по `(normalized_article, normalized_brand)`.
- **Slow Query:** Находил медленные запросы через логи базы, проверял план через `EXPLAIN ANALYZE`, смотрел, не идет ли `Seq Scan` там, где ожидался `Index Scan`.

### SQL оптимизация
**Upsert, JSONB, миграции:**
- **Batch Upsert:** Вместо тысяч `INSERT` мы делали один `INSERT ... ON CONFLICT DO UPDATE`. Чтобы не пересчитывать лишнее, сравнивали `content_hash` — если данные строки не поменялись, скипаем.
- **JSONB:** Отлично подошел для хранения вариативных конфигов поставщика (настройки FTP, селекторы браузера), так как схема у всех разная. Основные поля поиска лежали в строгих колонках.
- **Миграции (без даунтайма):** Добавить nullable колонку ➔ Писать в обе ➔ Плавно мигрировать старые данные мелкими батчами (Backfill) ➔ Переключить чтение ➔ Удалить старое. Главное — не взять долгий лок таблицы.

### Очереди
**Worker, retry, backoff:**
- **Зачем BullMQ:** Cron умеет запустить задачу — и всё. Если 100 поставщиков обновляются ночью, 100 тяжёлых процессов стартуют одновременно и сервер ложится. BullMQ: задачи в очереди, worker-ы разбирают по мере освобождения — не больше N параллельно.
- **Worker:** Берёт job, читает данные потоком, маппит, валидирует, пишет batch upsert в базу.
- **Retry/Backoff:** Сеть дёрнулась, API поставщика лёг — retry с exponential backoff. Важно: ошибки данных не ретраить бесконечно, разделять transient и validation errors.

### Redis/Kafka
**Cache/locks vs events:**
- **Redis:** Locks с TTL — не дать запустить два импорта одного поставщика параллельно. Временные статусы, rate limit. Источник истины — Postgres, не Redis.
- **Kafka:** BullMQ — «надо выполнить работу». Kafka — «факт произошёл». После импорта публикуем `supplier_offers.changed`, калькулятор цен подписан и пересчитывает асинхронно. Импорт не знает о существовании калькулятора — слабая связность.
- **Идемпотентность:** Kafka at-least-once — событие может прийти дважды. Защита: unique key + upsert в БД. Повторная обработка не создаёт дублей.

## 3. Проектные истории

### Import
**Поставщики, конфиги, mapping, worker-ы:**
Главная идея — из 100+ хардкодных скриптов сделать управляемый pipeline. Новый поставщик = JSON-конфиг (откуда забирать, маппинг колонок, лимиты, расписание). Worker-ы поделены по каналам: API, CSV/Excel, Playwright (headless browser), OCR. Нормализация и валидация — единое ядро для всех, логика не дублируется.

### Pricing
**Правила цены, версии, explain:**
Цепочка: закупка → наценка поставщика → наценка категории → логистика → скидка клиента. Все правила версионированы — можно откатить. Написали explain-алгоритм: точный лог всех накруток, чтобы менеджер видел в интерфейсе из чего сложилась цена 1250 руб., а не просто цифру.

### Сложности
**Большие файлы, дубли, отказы:**
- **Большие файлы:** Stream + batch. Файл любого размера с предсказуемым потреблением памяти.
- **Дубликаты:** Unique key в БД + `content_hash`. Повторный запуск не создаёт дублей и не триггерит лишние события downstream.
- **Отказы:** Кривая строка не роняет весь импорт. Пишем в rejected, идём дальше до `maxErrorsLimit`. 1 строка из 500k — не повод падать.

### Debug
**Как разбирать плохие строки:**
При подключении нового поставщика включали Debug Mode. База сохраняла Raw Row (как пришло от партнёра), Normalized Row (как смаппили) и причину rejected (например, пустой артикул). Разбор проблем интеграции — минуты вместо дней.

## 4. Качество и процесс

### Тесты
**Unit, integration, e2e, fixtures:**
- **Unit:** Логика маппинга, нормализации прайсов, генерация хэшей. Мокается всё.
- **Integration:** Запись в тестовую БД (Upsert), работа репозиториев, связка с брокером сообщений.
- **E2E:** Имитация полного цикла — дернуть ручку импорта, дождаться обработки очереди, проверить итоговую цену в базе.
- **Fixtures:** Эталонные куски CSV/JSON, моки ответов от чужих API для гарантии того, что парсер работает корректно.

### Review
**Что проверял в MR:**
Проверял не просто стиль кода, а надежность. Что будет, если воркер упадет посередине? (Идемпотентность). Нет ли `N+1` запросов к БД? Как расставлены индексы? Нет ли "умных" `any` в TypeScript? Не захардкожены ли секреты?

### Мониторинг
**Логи, метрики, инциденты:**
- **Логи:** Все логи связаны через `correlationId` и `importRunId`.
- **Метрики (Prometheus/Grafana):** Количество rejected строк, лаг в Kafka, длительность p95 выполнения батча, размер очереди BullMQ.
- **Инцидент:** Если выросла очередь, по метрикам сужаю зону поиска ➔ ищу по `correlationId` конкретный лог ➔ нахожу, что партнерский API начал отдавать 502, воркеры ушли в бесконечный retry.

### Git/CI
**Ветки, MR, pipeline:**
GitFlow (feature branch от develop ➔ MR ➔ Code Review ➔ Merge). CI Pipeline включает: `lint` ➔ `typecheck` ➔ `unit tests` ➔ `build` ➔ `docker image`. Никакого слияния при красных тестах.

### Docker/env
**Локальный запуск, секреты:**
Локально поднимали всю инфраструктуру (Postgres, Redis, Kafka) одной командой `docker-compose up`. Секреты (пароли от БД, API ключи) никогда не лежали в коде — пробрасывались через переменные окружения (.env локально или Vault в проде).

### Пакеты
**Общая библиотека, версии:**
Выносили общие DTO, контракты событий Kafka (чтобы Producer и Consumer не разъезжались), кастомные ошибки и хелперы. Придерживались SemVer: ломающие изменения только мажорными версиями. Старались не засовывать бизнес-логику одного сервиса в общий NPM-пакет.

## 5. Техника углублённо

### Парсинг
**Библиотеки Excel/CSV/XML:**
- **CSV:** `csv-parse` или `fast-csv` — потоковое чтение построчно, без загрузки всего файла.
- **Excel:** `exceljs` (streaming mode) или `xlsx` — для Excel важно смотреть на ограничения streaming, крупные файлы могут потребовать особого подхода.
- **XML:** `xml2js` для небольших файлов, потоковый XML-парсер для больших.
- **Важно:** Не читать весь файл `readFile`, а использовать stream/batch. Batch size брать из `limitConfig` поставщика.

### Browser
**Browser automation: Playwright/Puppeteer:**
> Когда нет API и данные доступны только через личный кабинет — используем headless browser.

- Логинимся, ждем нужный CSS selector, забираем таблицу или скачиваем файл.
- В разработке — headed mode, в production — headless.
- **Proxy rotation** для международных источников или ограничений по IP.
- В тестах держим HTML snapshots, чтобы не дергать реальный сайт в CI.

### OCR
**OCR и PDF:**
> Для PDF/сканов: вытаскиваем текст OCR-ом → приводим к табличному виду → прогоняем через тот же mapping/validation pipeline.

- OCR не пишет напрямую в offers. Он дает raw rows, нормализатор валидирует поля.
- Ключевой параметр — **confidence threshold**: строки ниже порога идут в rejected/debug на ручной разбор.
- Для спорных строк нужен debug mode с сохранением оригинального текста распознавания.

### Streams подробно
**Как не держать большой файл в памяти:**
- Читаем построчно через `for await...of` по async iterator.
- Копим accepted rows в batch до лимита, потом `batch upsert` в Postgres.
- После flush: `batch.length = 0` — освобождаем массив.
- `maxRows` и `maxErrors` задаются в `limitConfig` поставщика.
- Ошибочные строки не роняют весь импорт: пишем в rejected, продолжаем до лимита ошибок.

### Readonly
**TypeScript: readonly, as const:**
- `private readonly service` в конструкторе — DI-зависимость не перезапишется случайно.
- `readonly` поля в interfaces и DTO защищают от мутации данных.
- `ReadonlyArray<string>` или `readonly string[]` для массивов.
- `as const` для фиксации объекта/массива как литерального типа (например, список допустимых каналов).

### Load Script
**Load/rate script:**
> Для проверки поведения под нагрузкой использовал k6 или простой Node.js script с ограничением concurrency/RPS.

- Цель: проверить p95 latency, error rate, queue lag и поведение при burst.
- **Важно:** не DDoS-ить внешний API поставщика — использовать fixtures/mock.
- Для rate limit можно token bucket: N запросов в секунду.
- Сравнивать не только latency HTTP, но и время обработки очереди.

| Тема | Формулировка |
|------|-------------|

| **База** | Главная сущность — supplier_sources (конфиг) + offer_snapshot (unique key + content_hash) |

| **Validation** | `@ValidateNested({ each: true })` + `@Type(() => ChildDto)` для вложенных массивов |
| **TypeScript** | Union types + type guards для разных source config; generics для типизированных API responses |
| **Node.js** | I/O неблокирующий, CPU-heavy нельзя держать в event loop, большие файлы — stream/batch |
| **Git** | Маленькие MR, обязательный CI, review на бизнес-логику, индексы, ошибки, идемпотентность |
| **Пакет** | Общий package = контракты и типы, но не бизнес-логика одного сервиса |
| **Формула** | Контекст → Проблема → Решение → Почему → Результат |
